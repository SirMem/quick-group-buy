# 项目规范约定

本文记录当前已经拍板的项目约束。它不同于根目录 `CONTEXT.md`：`CONTEXT.md` 只维护业务语言；本文可以记录字段名、状态码、接口边界等工程约定。

## 跨上下文字段命名约定

同一笔商城支付订单在不同上下文/协议中会出现不同字段名，讨论时必须先明确所处上下文。

| 场景 | 字段名 | 规范含义 |
| --- | --- | --- |
| 商城支付侧 | `orderId` | 商城侧支付订单的商户订单号 |
| 支付宝侧 | `out_trade_no` | 支付宝回调/查询中携带的商户订单号 |
| 拼团营销侧 | `outTradeNo` | 调用方传入拼团营销系统的外部交易单号 |

约束：

1. 跨商城支付、支付宝、拼团营销协作时，必须用同一个值关联同一笔支付订单。
2. 在商城支付上下文中，这个值叫 **商户订单号**。
3. 在拼团营销上下文中，商城侧传来的 `outTradeNo` 统一叫 **外部交易单号**。
4. 前端展示或调用商城支付接口时，如果遇到 `orderId`，应理解为商城侧商户订单号；不要自行生成或改写。

## 商城支付侧支付订单状态

商城支付侧当前只认可以下支付订单状态：

| 状态码 | 规范名称 | 含义 |
| --- | --- | --- |
| `CREATE` | 创建完成 | 商城侧已创建支付订单，但可能还未生成支付链接 |
| `PAY_WAIT` | 等待支付 | 支付链接已生成，等待用户付款 |
| `PAY_SUCCESS` | 支付成功 | 支付渠道已确认用户付款 |
| `DEAL_DONE` | 交易完成 | 付款后的商品履约已经完成 |
| `CLOSE` | 超时关单 | 未支付订单已关闭，不能继续付款 |
| `MARKET` | 营销结算 | 拼团营销订单已完成拼团侧结算，等待或触发后续履约 |
| `WAIT_REFUND` | 营销退单待退款 | 已支付的拼团营销订单已进入退单流程，等待资金退款完成 |

约束：

1. 新增业务逻辑时，不得引入未定义的支付订单状态字符串。
2. 前端状态展示必须基于以上状态码做映射，不要从接口文案反推状态。
3. “支付成功”“营销结算”“交易完成”是三个不同阶段，不能合并成一个“完成”状态。
4. “退单”和“退款”必须区分：`WAIT_REFUND` 表示退单后等待退款，不等同于退款已经完成。

## Auth Token Conventions

- Refresh token 明文只返回给客户端，服务端只保存 SHA-256 hash。
- 一次扫码登录创建一个 `token_family_id`，表示一次登录会话。
- Refresh token 是一次性的；refresh 成功后旧 refresh token 标记为 `USED`。
- 成功 refresh 后旧 refresh token 必须写入 `revoked_at` 和 `replaced_by_token_hash`。
- 新 refresh token 必须继承旧 token 的 `token_family_id`。
- 旧 refresh token 二次使用返回未登录，并按严格复用检测吊销同一个 `token_family_id` 下仍 active 的 refresh token。
- Logout 只幂等吊销当前提交的 active refresh token，不默认吊销同一 openid 的其他会话。
- 未引入 Redis/access-token blacklist 前，logout 或 family 吊销只能阻断后续 refresh；已签发 access token 可能在 JWT 过期前仍有效。
- 前端应尽量对 refresh 请求做 single-flight/串行化；如果并发复用同一个旧 refresh token，后端会按严格复用检测处理，可能导致当前会话需要重新登录。
